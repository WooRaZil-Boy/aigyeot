아이곁 exec 갈래 성능 (2026-11-04) — 정적 자원 점검 + JVM 처리 시간(참고값)

목적: exec(app/src/main/kotlin/kr/aigyeot/app/exec/*.kt)가 만드는 스레드·리스너·오디오 자원·반복 작업을 코드로 하나씩 짝지어(만드는 곳 ↔ 놓는 곳) 새는 것과 평소에 도는 것이 없는지 본다. 무거운 순수 계산 부분의 처리 시간을 이 맥 JVM에서 재어 실시간 비율로 적는다.
기준: Pleos 성능 예산(주행 중 CPU 5% 미만·RAM 400MB 이하)과 경보 지연 3초 이하(명세서 15장), 스레드·리스너·서비스·AudioRecord·파일 핸들 해제, 불필요한 반복·폴링·백그라운드 작업이 없는지, 오디오 스레드·리스너·AudioTrack 해제와 폴링 대신 콜백.

방법:
  1) 정적 점검: 위 파일 전체를 읽고 생성·해제 짝을 `파일:줄`로 찾았다(실행 없음). 줄 번호는 브랜치 feat/car-exec 작업 트리(2026-11-04)의 값이다.
  2) JVM 시간(저장소 aigyeot-exec 루트). app/src/test/kotlin/kr/aigyeot/app/exec/ExecPerfScratchTest.kt를 임시로 만들어(재고 나서 지웠다, 남기지 않음) println으로 결과를 받았다:
     export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"; ./gradlew --console=plain :app:testDebugUnitTest --tests 'kr.aigyeot.app.exec.ExecPerfScratchTest'
     결과는 app/build/test-results/testDebugUnitTest/TEST-kr.aigyeot.app.exec.ExecPerfScratchTest.xml의 system-out(PERF 줄).
     각 항목은 예열 뒤 여러 번 재서 중앙값(System.nanoTime)을 썼다. WhiteNoise 1초 버퍼 100번 예열·200번, 50ms 버퍼 1000·2000번, Loudness·scale 3번 예열·7번, Sampler·RouteFeed·keepTail은 200만~500만 호출을 한 묶음으로 3번 예열·9번.
     기기: Apple M4 Pro 맥, Android Studio 번들 JBR(JVM).

읽는 법:
  - 표(1장)의 '놓는 곳'은 그 자원을 닫는 코드다. '정상'은 Exec.stop(), '끝·오류'는 재생이 끝나거나 오류·ReleaseAudio일 때, '예외'는 만드는 도중 던졌을 때다. ○=그 경로에서 놓음, △=조건부·메모 참고, ×=놓지 않음, -=해당 없음.
  - 2장의 realtime_ratio = 처리 시간 ÷ 그 오디오의 길이. 한 코어 대비 % = ratio × 100. 계속 도는 일(백색소음 생성)은 이 %가 곧 CPU 점유 추정이고, 한 번만 하는 일(3분 노래 측정)은 '3분 노래 한 곡을 처리하는 데 걸린 시간'이 의미 있는 값이고 %는 참고만 한다.

한계:
  - 에뮬레이터를 재지 않았다(사용자 결정: 호스트 연결이 합쳐진 뒤 잰다. 에뮬레이터는 다른 세션이 쓰는 중). 그래서 앱 CPU 5% 미만·RAM 400MB 이하(명세서 15장)와 경보 지연 3초 이하는 모두 미판정이다. 이유: 실제 AudioTrack·MediaPlayer·Pleos SDK 호출 비용, 스레드 수, 메모리 사용은 에뮬레이터에서만 볼 수 있다.
  - 2장 숫자는 맥(M4 Pro)의 JVM(HotSpot JIT)이다. 차 SoC·ART와 다르므로 차에서의 값이 아니고 참고값이다. 차에서는 더 느리다고만 알 뿐 몇 배인지 모른다(환산하지 않았다).
  - Sampler·RouteFeed·keepTail은 호출당 몇 ns로, JIT이 시험의 가짜 시계·가짜 post와 함께 인라인해 줄인 값일 수 있다. '순수 로직 비용이 무시할 만하다'는 뜻 이상으로 읽지 않는다. 실제 비용은 SDK 콜백·잠금·Handler 전달이 지배하며 이는 재지 못했다.
  - 정적 점검은 SDK 내부 동작(예: AudioTrack·MediaPlayer·TextToSpeech·NaviHelper의 release가 라우팅·이벤트 리스너를 스스로 정리하는지)을 이 환경에서 확인하지 못했다. 그 칸은 '명시 제거 없음(SDK 의존, 미확인)'으로 적었다.
  - 스레드 수·핸들 수·장시간 누수는 코드로 짝만 봤고 실행으로 세지 않았다.

  - 그 밖(내비·모드·TTS·STT·포커스)은 변화가 있을 때만 콜백이다.
  - 폴링: F19 확인 폴링(C:88) 하나뿐이고 차 제어 한 건 동안만 돈다(계약 4.2가 정한 것).

1-5. 예외 경로에서 놓이는지
  - Exec.stop(E:68~72): voice.cancel(말하기·듣기·tap·STT 묶음) → player.release(타이머·트랙·포커스) → io.stop(차 구독·내비·TTS·STT·스레드). 앞 단계가 던져도 뒤 단계가 안 도는 구조다(try/finally 없음). voice.cancel·player.release는 내부가 runCatching(P:125, P:128)이지만 voice.cancel의 tts.stop·stt.cancel(V:51~52)은 감싸지 않았다. TtsGate.stop(Gates:57)·SttGate의 SDK 호출은 runCatching(A:291~293)이라 실제로는 던지지 않는다. 그래서 문제로 올리지 않는다(3-4 메모).
  - Player: start 도중 던지는 곳 중 audio.hasRearOutput·requestFocus·open·track.start는 각각 잡아 reject(P:60, 65, 76, 82)하고 포커스를 놓는다(P:167). track.gain(P:90 apply)은 감싸지 않았다(3-2).
  - 재생 끝·오류·ReleaseAudio: end(P:172)·release(P:121)가 타이머 전부 취소→track.release→abandonFocus. end는 PlaybackEnded를 post, release는 사건 없음(계약 4.1).
  - 새 재생이 이전 재생을 덮을 때: Player.start:58이 먼저 end(STOPPED)로 놓고 시작한다.
  - NoiseTrack: 스레드가 write 중 오류면 exec로 넘겨 end→release(A:195→P:160).
  - FileTrack: 준비(prepare) 중 던지면 mp.release(A:238), 재생 중 오류는 A:233→P:160.
  - 노래 변환(SongLoudness): decode·transcode 모두 finally로 코덱·추출기·먹서 해제, 실패하면 .tmp 삭제.

== 3) 찾은 문제 ==
심각도: P1 안전·데이터 손실, P2 계약 위반·자원 누수·불필요한 상시 작업, P3 사소. 이번 점검에서 P1·P2는 찾지 못했다. 아래는 P3와 확인할 점이다(코드는 고치지 않았다).

3-1 (P3) Exec 생성만 하고 stop을 안 부르면 "exec" HandlerThread가 남는다. A:99(androidIo가 ExecThread를 만든다)·A:85. start()를 부르지 않아도 스레드가 시작되고, 닫는 길은 Exec.stop()뿐이다. 호스트가 서비스 종료·생성 실패 경로 모두에서 stop()을 불러야 한다(Exec 한 번 쓰고 새로 만든다는 E:41 규칙은 있으나 호스트 연결은 아직 없음). 호스트가 합쳐질 때 확인.

3-2 (P3) Player.start:90의 apply(→track.gain)는 감싸지 않았다. 던지면(예: 오류 상태가 된 MediaPlayer.setVolume의 IllegalStateException) Exec.handle의 catch(E:93)가 PlaybackRejected만 낸다. 이때 cur(P:80)은 지워지지 않고 트랙도 놓지 않는다(타이머도 아직 안 걸림). 백색소음 쓰기 스레드는 이득 0(A:202 setVolume 0)으로 계속 돈다. 다음 StartPlayback(P:58)이나 ReleaseAudio에서야 놓인다. 발생 조건이 드물고 소리는 나지 않아 안전 문제는 아니다. 고친다면 P:89~92를 try로 감싸 reject 경로(P:82와 같은 cur=null·release)로 보낸다.

3-3 (P3) initialize 콜백이 stop보다 늦으면 해제된 객체에 리스너를 건다. A:271~277(TTS), A:305~306(STT), A:520~521(내비). ex.guard가 예외는 삼키므로 새지는 않으나, SDK가 release 뒤 addListener를 받으면 어떻게 하는지는 확인 못 했다(미확인). stop이 start 직후 불리는 경우(서비스가 금방 꺼짐)에만 해당한다.

3-4 (P3) Exec.stop(E:68~72)은 단계마다 try가 없어 voice.cancel이 던지면 player.release·io.stop이 안 돈다. 실제 던질 곳(tts.stop·stt.cancel)은 각각 runCatching(Gates:57, A:291~293)이라 지금은 던지지 않는다. 방어만 하는 의견이다. 고치기보다 호스트가 stop 예외를 잡는지 확인하면 충분하다.

3-5 (해결, 4회차) Controls에 일괄 닫기 closeAll이 생겼다. Exec.stop이 진행 중인 F19 작업(ok=false)·경유지 작업을 닫고 타이머를 취소한다. ExecThread는 stop 뒤 start가 다시 오므로 끝내지 않으며(quitSafely를 부르지 않는다), 예약은 부품이 stop에서 직접 취소한다.

3-6 (P3) FileTrack.init의 prepare()(A:237)는 동기 호출이다. Exec.handle(StartPlayback)이 이 호출이 끝날 때까지 exec 잠금을 쥐고 호출한 스레드(엔진 쪽)를 붙잡는다. E:40~41의 "[handle]은 빨리 돌아온다"와 부딪힐 수 있고 경보 지연 3초 예산에 들어간다. 자장가 assets·노래 로컬 파일이라 보통 짧을 것으로 보이나 지연은 재지 못했다(미측정, 에뮬레이터에서 StartPlayback→PlaybackStarted 시간을 재야 한다). NoiseTrack.start의 첫 무음 write(A:204)도 같은 성격이다.

3-7 (P3) NoiseTrack.release의 join(300)(A:217)은 호출한 스레드가 exec 잠금을 쥔 채 최대 300ms 기다린다(Player.end·release는 잠금 안). 그동안 다른 콜백이 기다린다. Exec.stop이 메인 스레드에서 불리면 메인이 최대 300ms 막힌다. 평소에는 stop으로 write가 바로 깨어나므로 훨씬 짧을 것이다(미측정).

3-8 (P3) SongLoudness.makeCopy(S:26)는 withContext(Dispatchers.IO) 안의 블로킹 반복이라 코루틴 취소를 확인하지 않는다. link가 작업을 취소해도 디코드·인코드가 끝까지(또는 MAX_IDLE 한계까지) 돈다. 취소 뒤 output이 남는지는 link 쪽 처리에 달렸다. 3분 노래를 디코드 3번 하는 것(S:36 measureScaled, S:137 measure, S:204 transcode)도 비용이다. 이 변환은 노래 한 곡을 받을 때만 하는 일이다.

3-9 (P3, 확인할 점) "noise" 쓰기 스레드는 우선순위를 올리지 않았다(A:177, 기본 스레드). 버퍼가 200ms(A:170)라 여유는 있으나, 차에서 다른 부하가 많을 때 끊김이 나는지는 에뮬레이터·실차에서 들어봐야 안다(미측정).

3-10 (P3, 확인할 점) TTS 직렬화(Gates:29~30, WARM_MS 3초)에서 시작 직후 예열 끝 신호가 안 오면 그 동안 도착한 첫 문장이 최대 3초 늦다. 경보 지연 3초 예산과 같은 크기라 시작 직후에는 걸릴 수 있다(평상시 예열은 짧을 것으로 보이나 미측정). stop 뒤 SETTLE_MS 1초(Gates:87)도 다음 문장을 미룬다. 둘 다 설계값(근거 없음 표시되어 있음)이고 에뮬레이터에서 재야 판정된다.

3-11 (P3) 속도 구독이 SENSOR_RATE_FAST(A:434)이고 Sampler는 받은 뒤 100ms 이하 간격을 버리는 방식이다(Feeds:91). 구독 단계에서 빈도를 줄이는 것이 아니라 SDK가 보내는 만큼 콜백 비용(잠금·람다)을 치른다. 빈도(FAST가 몇 Hz인지)는 이 환경에서 확인하지 못했다(미확인). 에뮬레이터 CPU를 잴 때 속도·조향 콜백의 몫을 따로 보면 된다.

다음에 에뮬레이터로 잴 것(호스트 연결이 합쳐진 뒤): 주행 장면 dumpsys cpuinfo·meminfo(CPU 5% 미만·RAM 400MB 이하), StartPlayback→PlaybackStarted 시간(3-6), 백색소음 재생 중 스레드 수(/proc/<pid>/task)와 정지 뒤 줄어드는지(A:177·A:94), AudioTrack·MediaPlayer 해제 뒤 오디오 서비스 세션(dumpsys audio), 열린 파일 핸들(/proc/<pid>/fd) 수의 재생 반복 전후 비교, 속도 콜백 빈도(3-11).
